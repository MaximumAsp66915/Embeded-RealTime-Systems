# Section 2 — Caching and Two-Layer Database Structure

Builds directly on Section 1: the same Master/2-Slave cluster, now with a
**Memcached** cache layer in front of each node's SQLite database. Every
lookup checks the cache first; only a cache miss touches SQLite, and
that result is written back into the cache for next time. The Master
and both Slaves each run their own local Memcached instance — this is a
per-node cache, not a shared one. The NGINX port-based addressing set up
in Section 1 (Master `8001`→self, `8002`→Slave 1, `8003`→Slave 2) is
unchanged and still how the operator and the Master's own cascade reach
every node — see `../Phase1/Report.md` Section 6 if you're setting the
cluster up from scratch. **Note:** `../Phase1/master/run.sh` has since
been extended to configure NGINX automatically, but this section's own
`master/run.sh` still expects it configured manually first, using the
original scheme (`SLAVE1_PORT`/`SLAVE2_PORT` = NGINX's fixed `8002`/
`8003`) — see `../Phase1/README.md`'s warning banner before running
this section's `master/run.sh` if you're setting up NGINX for the first
time.

```
Phase2/
├── master/
│   ├── src/main.cpp     # master_node — cache-first gateway + local DB + cascade
│   ├── Makefile
│   ├── env               # generated by run.sh (PORT, DB_PATH, SLAVE1_PORT, SLAVE2_PORT)
│   └── run.sh              # installs deps incl. Memcached, configures, compiles, runs
├── slave/
│   ├── src/main.cpp      # slave_node — cache-first lookup over its own local DB
│   ├── Makefile
│   ├── env                 # generated by run.sh (PORT, DB_PATH)
│   └── run.sh                # installs deps incl. Memcached, configures, compiles, runs
├── client_tests/
│   ├── value_test.sh          # curl-based correctness regression test (same cases as Section 1)
│   └── speed_test.sh          # two-round cache-miss vs cache-hit benchmark
├── figure/                     # screenshots referenced in Report.md
├── README.md                    # this file
└── Report.md                     # two-layer cache design, speed test analysis, figures
```

> **Note on the proposed layout:** this bundle uses one `run.sh` per node
> (which installs *and* starts Memcached, see item 2 below) in place of
> separate `db_init_*.sh` / `memcached_init_*.sh` / `config.example`
> files, and `client_tests/{value_test.sh,speed_test.sh}` in place of
> `scripts/{build_and_run.sh,benchmark_read.sh}`. See **"Known gaps"**
> in `Report.md` for what that means in practice.

## 1. How to install Memcached

Each node needs both the Memcached **server** and the **libmemcached**
client library the C++ code links against. `master/run.sh` and
`slave/run.sh` do this for you automatically (checking for
`/usr/include/libmemcached/memcached.h` and the `memcached` binary, and
installing both packages if either is missing), but to do it by hand on
Ubuntu 22.04:

```bash
sudo apt update
sudo apt install -y memcached libmemcached-dev
```

`memcached` is the actual cache daemon; `libmemcached-dev` provides the
headers/library (`-lmemcached`) that `master_node`/`slave_node` are
compiled against.

## 2. How to run Memcached

Memcached installs as a systemd service and normally starts
automatically, but `run.sh` explicitly makes sure of it on every run:

```bash
sudo systemctl start memcached
sudo systemctl enable memcached   # start automatically on boot
sudo systemctl status memcached   # confirm it's active (running)
```

By default it listens on `127.0.0.1:11211` — loopback only, which is
exactly what's needed here since each node only ever talks to its
*own* Memcached instance (`CacheManager::init("127.0.0.1", 11211)` in
both `main.cpp` files); there is no cross-node cache sharing.

## 3. How to compile the programs

Same as Section 1, plus the `-lmemcached` link flag (already in both
Makefiles):

```bash
# Master
cd master
make clean && make        # produces ./master_node

# Slave (same steps on each slave checkout)
cd slave
make clean && make        # produces ./slave_node
```

## 4. How to run the Master and Slave programs

Same prompts as Section 1's `run.sh`, plus the automatic Memcached
install/start step from item 2 — run the slaves first, then the Master:

```bash
# On Slave 1's VM
cd slave
./run.sh
# Enter Binding Port for this Slave [8080]: 8080
# Enter local SQLite database path [../slave1.db]: ../slave1.db

# On Slave 2's VM
cd slave
./run.sh
# Enter Binding Port for this Slave [8080]: 8080
# Enter local SQLite database path [../slave1.db]: ../slave2.db

# On the Master's VM (NGINX from Section 1 already installed + reloaded)
cd master
./run.sh
# Enter Gateway Binding Port for Master [8080]: 8080
# Enter target Master SQLite DB path [../master.db]: ../master.db
# Enter Target Slave 1 Communication Port [8002]: 8002
# Enter Target Slave 2 Communication Port [8003]: 8003
```

Each program logs `[STARTUP] Memcached structural connectivity
established successfully.` once it's confirmed it can reach its local
cache daemon, then runs in the foreground exactly as in Section 1.

## 5. How to send a request

Same endpoint as Section 1, through the Master's NGINX on `8001` — the
only change is the **response body**, now JSON with the value, where it
came from (`CACHE` or `DB`), and how long the lookup took inside the
node that answered:

```bash
curl "http://192.168.56.101:8001/query?type=temperature&id=101"
# First time:  {"value":"24.8","source":"DB","response_time_ms":2.417}
# Second time: {"value":"24.8","source":"CACHE","response_time_ms":0.083}
```

## 6. How to run the speed test script

`client_tests/speed_test.sh` reads the same set of sensors twice in a
row against the Master and prints the round-trip time for each request:

```bash
cd client_tests
./speed_test.sh
# Enter Master Node IP [192.168.56.101]:
# Enter Master Node Port [8001]:
```

It flushes Memcached (`flush_all` over the `memcached` text protocol on
port `11211`) immediately before Round 1, so Round 1 is a guaranteed
cache-miss baseline, then repeats the identical queries in Round 2,
which should hit the cache populated by Round 1. **Run this script
directly on the Master VM** — the `flush_all` targets `127.0.0.1:11211`,
i.e. whichever machine runs the script; from any other machine it
flushes a local Memcached that isn't part of the cluster (or nothing at
all), and Round 1 may end up hitting stale cache from an earlier run.
See `Report.md` for the full explanation and measured results.

`client_tests/value_test.sh` re-runs Section 1's correctness checks
(same sensor IDs and expected values) against the new JSON response
format, to confirm caching didn't change *what* answer comes back —
only how fast.

## 7. Analysis of the test results

Full breakdown — including the actual Round 1 vs. Round 2 timings, why
a couple of entries can still miss the cache on Round 2, and how the
Master's cache differs from each Slave's — is in `Report.md` Section 4. In
short: Round 1 answers are all `"source":"DB"` at single-digit-to-low-
double-digit millisecond latency (SQLite open + parameterized query
each time); Round 2 answers are `"source":"CACHE"` at sub-millisecond
latency for everything that got cached in Round 1, since a Memcached
`GET` on localhost skips SQLite, the filesystem, and query planning
entirely.
